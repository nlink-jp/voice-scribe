# ADR-0005: 固有名詞の誤認識を復号側で直さない

- Status: Accepted
- Date: 2026-08-09

## Context

v0.1.3 で、`--prompt`（whisper の initial prompt）では**特定の固有名詞の聞き間違いを
直せない**ことが実測で確定した。実音声で姓が一貫して誤って出るのに対し、正しい綴りを
含む 4 通りのプロンプト（漢字・カタカナ・列挙・文中）がいずれも失敗し、一部は他の
正しい行を壊した。

そこで残った候補が whisper.cpp の `whisper_full_params.grammar_rules` である。AGENTS.md に
「語彙を本当に拘束したいならこれが機構だ」という手がかりを残した。**この ADR はその
手がかりを検証した結果である。**

`--prompt` を「Cheap and effective」と実測なしに書いて概ね逆だった直後なので、今回は
**先に上流の実装を読み、実音声で測ってから**書く。

## 機構（上流ソースの確認）

submodule の pin である whisper.cpp `592feef0` を読んだ。

1. **文法は語彙ではなく、セグメント全体の形を拘束する。** `root` は 30 秒窓の出力
   **全体**を受理しなければならない。同梱の文法例（`colors.gbnf` / `assistant.gbnf` /
   `chess.gbnf`）はすべて閉じたコマンド集合で、`command` と `wchess` の例から使われる。
   これが設計上の用途である。

2. **penalty はソフトで、減点しかしない。** `whisper_suppress_invalid_grammar` の実体は
   `logits[reject.id] -= grammar_penalty`（既定 100.0）の一行だけ。**文法に合うトークンを
   持ち上げる処理は無い。** 触られるのは「文法が拒否したトークン」のみである。

3. **EOT への減点は無効化されている。** 「文法が継続を許すとき EOT を減点する」ブロックは
   上流でコメントアウトされたまま。つまりデコーダは**セグメントを早期に打ち切ることで
   文法から逃げられる**。

4. **文法は 30 秒窓ごとに初期化される**（各反復でデコーダに `whisper_grammar_init`）。
   窓をまたいだ制約は書けない。

5. `--grammar` を渡すと**サンプリングが beam search に切り替わる**（cli.cpp）。素朴に
   比較すると、文法の効果と探索戦略の効果が混ざる。

(2) から予測が立つ。**許容的な文法に名前を選択肢として足しても、何も拒否されないので
何も起きない。** 以下はこの予測の検証である。

## 実測

2026-08-09、M2 Max / macOS 26.6.1。上流の `whisper-cli` を pin から別ツリーに建てて使用
（リポジトリの `build/` には触れていない）。実音声 50 秒、日本語、beam size 5 を全条件で
固定（(5) の交絡を除くため）。この 50 秒には問題の姓が 3 回出てくる。

姓は以下 **N** と書く（正しい表記も誤った表記も、実測の内容には関係しない）。

| # | 文法 | 出力 |
|---|------|------|
| A | なし | 通常の転記。**N は 3 回とも誤って**出る |
| B | `piece ::= N \| [^\x00]`（N + 何でも） | **A とバイト単位で同一** |
| C | 閉じた語彙 7 語（N を含む） | **50 秒が 2 文に潰れ**、N は一度も出ない |
| D | C + `--grammar-penalty 10` | C と同一 |
| E | `root ::= N [^\x00]*`（先頭固定） | **N の 1 文字目だけ**出して打ち切り |

A と B の同一性は**モデルを変えても成立した**（`ggml-base-q5_1` と、手元に残っている
`kotoba-whisper-v2.2-ggml-q5_0`（ADR-0004 の通り作者の v2.0 とバイト同一）の 2 本）。

読み取れること:

- **B は無効果**。予測どおり、許容的な文法は何も拒否しないので何も起きない。
  「語彙を宣言する」用法は**存在しない**。
- **C は効いた。ただし壊れた。** 機構自体は動く — 出力は許可語彙の中に落ちる。しかし
  50 秒の会話が 2 文になり、**音声に 3 回出てくる N は一度も出なかった**。語彙に入れて
  あってもである。
- **D で penalty を 1/10 にしても C と同じ。** 減点の強さの問題ではない。
- **E は機構 (3) の実演**。先頭を固定すると 1 文字で打ち切る。文法を満たすより
  セグメントを終わらせるほうが安いので、デコーダはそちらを選ぶ。

つまり grammar-constrained decoding は、**開いた転記に語彙のヒントを与える機構ではない。**
閉じた集合しか言わないと分かっている音声を、その集合に押し込む機構である。我々の用途
（何を言うか分からない会話の転記）には原理的に合わない。

## Decision

### 1. 復号に文法制約は入れない

`--grammar` は追加しない。v0.1.3 で残した「grammar_rules が本来の機構」という手がかりは
**誤りだったので取り消す**（AGENTS.md を訂正する）。

上流の EOT 減点をローカルで有効化して (3) を回避する道は取らない。上流が意図的に
無効化しているものを我々のビルドだけで変えると、submodule 更新のたびに壊れる。

### 2. 固有名詞の修正は**エージェント側**の仕事とし、voice-scribe は持たない

当初この ADR は「置換表を voice-scribe に持ち、metadata に記録する」ことを提案していた。
**取り下げる。** 理由は 2 つある。

- **列挙できた綴りしか直せない。** 同一の姓が実測で **5 通り**の異なる誤りに割れた
  （ひらがな・カタカナ・長音入り・別漢字）。**登場人物を把握しているエージェントは、
  誰も列挙していない 6 通り目も文脈から直せる。** 置換表にはそれができない。
- **来歴の懸念は成立しない。** 提案の根拠は「エージェントが書き換えると、聞き取りと
  修正の区別が付かなくなる」だったが、**voice-scribe が書いた転記ファイルは手つかずで
  残る**。差分はいつでも取れる。voice-scribe が置換を代行する必要はない。

voice-scribe の責務は「**直せる転記を返すこと**」に留める — 正確なタイムスタンプ、
実際の発話に対応するセグメント、そして結果が怪しいときに黙らないこと（v0.1.3 の
過剰分割警告）。意味の解釈は、文脈を持つ側でしかできない。

### 3. 文法制約が戻ってくる条件

閉じたコマンド認識（音声コマンド、定型の読み上げ確認）を作るときは有効な機構である。
その時は**別機能**として GBNF ファイルをそのまま渡す形にする。汎用転記のオプションに
混ぜない — C と E がその理由である。

## Consequences

- README の「stubborn な名前は転記後に直せ」という記述は正しかった。2 はその「誰が」を
  決めたということ — voice-scribe ではなく、文脈を持つ下流である
- **前処理でも直らない。** 音源分離を実測したが名前は変わらなかった（ADR-0006）。
  固有名詞は音響側の問題ではない
- AGENTS.md の grammar への言及を訂正する必要がある（本 ADR へのリンクに置き換える）
- 「復号側で語彙を拘束する」方向の検討はこれで打ち止め。同じ道を再び歩まないために、
  効かなかった条件（B・D）を上の表に残す
- 上流の `whisper-cli` を建てる手順が実測に有用と分かった。今後、我々の Go ブリッジが
  公開していないパラメータの効果を測るときは同じ手が使える
