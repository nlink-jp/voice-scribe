# ADR-0004: サプライチェーンの検証方針

- Status: Accepted
- Date: 2026-08-08

## Context

v0.1.0 リリース後、「submodule をリリースタグに PIN しておきたい、サプライチェーン攻撃が
怖いので」という指摘を受けて、ビルド時・実行時に取得する第三者成果物を棚卸しした。

結論から言うと、**当初 PIN しようとしていた場所は問題ではなく、別のところに穴があった**。

## 棚卸し結果

| 取得物 | いつ | 検証 (v0.1.0 時点) |
|---|---|---|
| whisper.cpp | ビルド時 (submodule) | git SHA — **content-addressed で改竄不可** |
| sherpa-onnx | ビルド時 (submodule) | git SHA + リリースタグ (ADR-0002) |
| ONNX Runtime prebuilt zip | ビルド時 (`make deps`) | SHA256 検証あり (ADR-0002) |
| **モデルファイル（8種）** | **実行時 (`models pull`)** | **サイズのみ** ← **穴** |

## Decision

### whisper.cpp はリリースタグに戻さない

指摘を受けて `v1.9.2` への PIN を検討したが、**現在の pin `592feef0` は v1.9.2 の 17
コミット先で、その中に 2 件のメモリ安全性修正が含まれている**:

- `8631825d` — `log_mel_spectrogram` が 201 サンプル未満の音声でヒープ外読み出し。
  **任意のユーザー音声を食わせるツール**であり、MCP 経由なら細工ファイルも届く
- `df1547b6` — 不正な `n_dims` を持つ壊れたモデルファイルでスタックバッファオーバーフロー。
  **モデルをネットからダウンロードするツール**であり、まさにサプライチェーン経路

v1.9.2 に戻すとこの 2 件を失う。**リリースタグであることより、既知の脆弱性修正を
含んでいることが優先する。**

また前提の整理として、**git submodule は既に commit SHA で固定されており、SHA は
content-addressed なので改竄に対してはタグ名より強い**（タグは動かせる）。リリースタグに
することで増えるのは主に監査可能性（CVE との突き合わせ）であり、改竄耐性そのものではない。

したがって: **リリース版が出たらそこへ移る。それまでは修正入りのコミットに留まる。**
どちらの場合も不変の SHA で固定する点は変わらない。

### モデルファイルは SHA256 で検証する（本題）

**v0.1.0 の検証はサイズのみだった。** サイズは、ファイルを差し替えられる攻撃者が
容易に維持できる。そして `df1547b6` が示すとおり、**壊れたモデルファイルはメモリ安全性の
問題**であって「間違った文字起こしが出る」で済む話ではない。

Hugging Face は全 LFS ファイルの SHA256 を公開している（`?blobs=true` の `lfs.sha256`）。
カタログの全エントリにこれを pin し、次の 2 経路で検証する:

1. **ダウンロード時** — rename の**前**に検証するので、失敗したファイルは一瞬たりとも
   正規のパスに存在しない
2. **既存ファイル再利用時** — `models pull` がサイズ一致で DL を省く経路。**ここを
   素通りさせるとサイズだけの検査が「検証したつもり」になる**ので、こちらもハッシュを見る。
   不一致は黙って再 DL せずエラーにする（サイズが合っていて中身が違うファイルの存在は、
   運用者に知らせる価値がある）

テストでは**同一サイズで中身だけ差し替えた**ケースを明示的に落としている。

### 既定モデルは作者のリポジトリから取る

ハッシュを集める過程で、カタログの 2 エントリが**バイト単位で同一**だと判明した:

```
kenrouse/kotoba-whisper-v2.2-ggml/kotoba-whisper-v2.2-ggml-q5_0.bin
kotoba-tech/kotoba-whisper-v2.0-ggml/ggml-kotoba-whisper-v2.0-q5_0.bin
→ size / sha256 / blobId すべて一致
```

つまり **「v2.2」を名乗る第三者の再アップロードが、作者の v2.0 と同じ中身を配っていた**。
voice-scribe はそれを**既定モデル**にしていた。

対処:
- 既定は `kotoba-tech`（作者）の `kotoba-whisper-v2.0` に変更
- 重複エントリを削除（同じ中身に 2 つの名前を付けたカタログは、選択肢について嘘をつく）
- **破壊的変更**: 既定モデル名が `kotoba-whisper-v2.2` → `kotoba-whisper-v2.0`

一般則として、**既定で入るものは上流の作者から取る**。ミラーは、作者が配っていないか、
作者の配布形式が使えない場合に限る。

## Consequences

- カタログの全 7 エントリが 64 桁の SHA256 を持つ（テストで固定）
- 同一ハッシュのエントリが 2 つ存在しないことをテストで固定
- 既定の日本語モデルが `kotoba-tech/` 由来であることをテストで固定
- `models list --json` が `sha256` を出すので、利用者が手元で照合できる
- 破壊的: `default_model` の既定値と `models pull` の引数が変わる

### 残る露出（受容）

- **ONNX Runtime の prebuilt zip は第三者個人のリポジトリ**（`csukuangfj/onnxruntime-libs`）
  から取得している。SHA256 は検証しているが、そのハッシュ自体は sherpa-onnx の pin 由来
  なので、信頼の起点は「submodule を固定した時点の上流」になる（TOFU）。Microsoft の
  公式配布に静的リンク用のビルドが無いため、現状は代替が無い
- モデルのハッシュも同様に「カタログを書いた時点の HF」を起点とする TOFU である。
  ただし**起点が固定される**ことに意味があり、以後の差し替えは検出できる
